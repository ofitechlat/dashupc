# Backend Documentation & Architecture

This document serves as a reference for the backend architecture, database schema, and security policies of the Tutoring App. It is intended for current and future developers (human or AI) to understand the system structure and avoid common pitfalls.

## 1. System Overview

- **Backend Logic**: Hybrid approach.
    - **Next.js API Routes** (`app/api/*`): Use for lightweight operations, Auth hooks, and direct frontend-to-db interactions via Supabase Client.
    - **Python FastAPI** (`backend/main.py`): Handles heavy compute tasks (Video Processing, AI Summaries) and complex logic not suitable for Edge Functions.
- **Database**: PostgreSQL (hosted on Supabase).
- **Authentication**: Supabase Auth (GoTrue). Users are linked to `students` or `tutors` tables via `user_id`.

## 2. Database Schema

### Core Tables

#### `students`
- `id` (UUID): Primary Key.
- `user_id` (UUID): Links to `auth.users`. **Critical for RLS**.
- `name`, `email`, `phone`: Profile info.
- `must_change_password` (BOOLEAN): Forces password change on first login.

#### `tutors`
- `id` (UUID): Primary Key.
- `name`, `email`, `specialties` (JSONB): Profile info.
- `video_meeting_url`: Static meeting link (Zoom/Meet).

#### `subjects` (Materias)
- `id` (UUID): Primary Key.
- `name`, `syllabus` (JSONB): Course content structure.
- `individual_price`, `group_price`: Pricing logic.

#### `course_requests`
- `id` (UUID): Primary Key.
- `student_id` (UUID): FK to `students`.
- `subject_id` (UUID): FK to `subjects`.
- `status`: ENUM ('pending', 'matched', 'rejected', 'cancelled').
- `payment_status`: ENUM ('pending', 'partial', 'paid', 'overdue'). **Added in Migration 03**.
- `total_price`, `amount_paid`: Financial tracking.

#### `classes` (Sessions)
- `id` (UUID): Primary Key.
- `request_id` (UUID): FK to `course_requests`. **Links session to financial package**.
- `student_id`, `tutor_id`: FKs.
- `date`, `start_time`, `end_time`: Scheduling.
- `status`: 'scheduled', 'completed', 'cancelled'.

## 3. Row Level Security (RLS)

Security is handled at the database layer using Postgres RLS Policies.

**Critical Rule**: The application uses the **Supabase Client** (`@supabase/supabase-js`) on the frontend. This client respects RLS. If a user cannot see data, it is 99% likely due to a missing or incorrect RLS policy.

### Policies (as of Migration 04)

- **Students**:
    - Can view their own profile: `auth.uid() = user_id`.
    - Can view their own requests: `student_id` lookup matches `auth.uid()`.
    - Can view their own classes: `student_id` lookup matches `auth.uid()`.

- **Admins**:
    - Identified by email (e.g., `506casm@gmail.com`) via JWT claim.
    - Have FULL access (`USING (true)` or specific email check) to all tables.

## 4. Common Issues & Fixes

### "Could not find column in schema cache"
- **Cause**: A migration added a column (e.g., `request_id`), but the Supabase PostgREST server hasn't refreshed its cache.
- **Fix**: Go to Supabase Dashboard > Settings > API > **Reload Schema Cache**.

### "404 on Edit Page"
- **Cause**: Next.js App Router requires specific folder structure `app/[resource]/[id]/edit/page.tsx`.
- **Fix**: Ensure the directory structure matches the route.

### "Student cannot see data"
- **Cause**: RLS policy missing or `user_id` is NULL in `students` table.
- **Fix**:
    1. Check if `students.user_id` is set.
    2. Check if a Policy exists for `SELECT` on the target table.

## 5. API Patterns

- **Filters**: Passed as query params (e.g., `?subject_id=...`).
- **Joins**: Use Supabase recursive select (e.g., `*, student:students(*)`).
- **Payment Updates**: Handled via `PATCH` to `course_requests`.
